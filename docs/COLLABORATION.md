# 协作规范

> 本文档定义 AI 辅助开发时的协作约定，与技术实现无关。

## 数据单向流动 (Single Source of Truth)

> **数据有一个来源，单向流动。多份副本 = 漂移 = bug。**

- 主进程是唯一数据源（拥有 webContents、SQLite 等）
- 渲染进程是纯展示层，被动接收主进程推送
- **三条具体规则：**
  1. 主进程推送事件前要预过滤，不要让渲染进程过滤
  2. 不要在数据结构中缓存派生状态（如 `canGoBack`），按需查询
  3. 渲染进程 invoke 后等待主进程 push，不要自行修改状态

## 不懂就问

- 对需求有疑问，先问清楚再动手
- 对实现不确定，先问用户确认
- **不要假设，要验证**

## 方案对比

- 实现功能时提供 **2-3 个主流方案**
- 每个方案说明：优点 / 缺点 / 适用场景
- 用户决策后记录理由

## 修改前三件事（跨项目同步）

| 修改类型 | 检查项 |
|---------|--------|
| 修改协议 | `electron/main.ts` + `electron/env.ts` + 子应用路由 |
| 新增 IPC 模块 | 模块实现 / preload 注册 / main 注册 |
| 新增子应用 | 扩展子应用地图 + subapp 配置 |

## Review 要对照流程图

- 不能只"扫一眼"，要对照 Stage 1 流程图验证分支覆盖
- 重点检查：异常路径、边界条件、与原意偏离
- 反问验证：
  - "删掉这段会怎样？" — 验证必要性
  - "X 场景下走哪个分支？" — 验证覆盖度

## YAGNI 原则

- **主动建议删除**过度抽象，不是添加
- 问自己："这个间接层真的在解决当前问题吗？"
- 命名用直接动词，不用前缀模式（如 `markX`）
- 三步协议是坏味道，主动提议压缩到两步

## 决策理由要记录

- 产出不只是"选了 A"
- 要写 **"为什么不选 B/C"**
- 写入任务说明，后续回看有据

## 功能完成要产出模块文档

模块 md 模板：
```
## 目的
## 接口
## 关键流程（附流程图链接）
## 假设
## 依赖
## 已知限制
```

## TDD 规则 (Red → Green → Refactor)

> 新增功能或修复缺陷时，遵循以下流程：

**三阶段循环：**
1. **Red** — 先写测试，确认测试正确失败
2. **Green** — 编写最小实现使测试通过
3. **Refactor** — 在测试保护下重构

**强制规则：**
| 规则 | 说明 |
|------|------|
| 回归测试 | Bug 修复必须包含回归测试，防止再次发生 |
| 禁止削弱测试 | 禁止通过删除、跳过或削弱测试来通过验证 |
| 运行测试 | 完成后运行相关测试 |
| 无法测试时 | 说明原因和风险 |

**免于 TDD：** 纯样式、文案、配置或无法合理自动测试的改动。
